# Бизнес-логика приложения `new-gorisons`

## Назначение документа

Этот документ является главным источником истины по бизнес-логике приложения.

Он нужен, чтобы:
- зафиксировать продуктовую модель;
- описать роли, сущности и правила доступа;
- отделить реализованное поведение от целевого;
- дать Cursor опору для безопасного развития доменной логики.

Если код противоречит этому документу:
- для бизнес-решений приоритет у этого документа;
- для технических деталей реализации нужно сверяться с кодом.

## Что это за продукт

`new-gorisons` - это платформа услуг.

На платформе есть два основных режима пользователя:
- заказчик: ищет и просматривает услуги;
- профессионал / поставщик услуг: создает профессиональный профиль и управляет услугами от имени этого профиля.

Текущая продуктовая модель:
- публичная часть показывает каталог услуг;
- зарегистрированный пользователь может остаться обычным заказчиком;
- зарегистрированный пользователь может создать профессиональный профиль;
- профессиональный профиль может быть личным (`SELF_EMPLOYED`) или корпоративным (`COMPANY`);
- все управляемые профессиональные данные принадлежат конкретному `Provider`.

## Основные роли

В системе есть два уровня ролей.

### Системные роли

Системная роль действует на всю платформу и хранится в `User.systemRole`.

Поддерживаются роли:
- `PLATFORM_ADMIN` - администратор платформы;
- `CUSTOMER` - обычный пользователь.

Правила:
- новый пользователь по умолчанию создается как `CUSTOMER`;
- `PLATFORM_ADMIN` имеет полный доступ ко всем данным платформы;
- системная роль не заменяет membership внутри provider, а существует параллельно с ним.

### Роли внутри provider

Доступ к данным поставщика выдается через `ProviderMember`.

Поддерживаются роли:
- `OWNER` - владелец профессионального профиля;
- `MANAGER` - менеджер профессионального профиля.

Статусы membership:
- `INVITED`;
- `ACTIVE`;
- `SUSPENDED`.

В доступе участвуют только membership со статусом `ACTIVE`.

## Основные сущности домена

### User

Пользователь платформы.

Ключевые поля:
- `id`;
- `email`;
- `name`;
- `systemRole`;
- `activeProviderId`.

Смысл:
- пользователь может быть только заказчиком;
- пользователь может состоять в одном или нескольких provider;
- `activeProviderId` задает текущий рабочий контекст профессионала.

### Provider

Профессиональный профиль поставщика услуг.

Ключевые поля:
- `id`;
- `name`;
- `slug`;
- `type`;
- `ownerUserId`.

Типы:
- `SELF_EMPLOYED` - самозанятый / физлицо;
- `COMPANY` - компания / организация.

Смысл:
- это бизнес-сущность, от имени которой публикуются и управляются услуги;
- именно `Provider` является владельцем provider-данных;
- один пользователь может иметь membership в нескольких provider.

### ProviderMember

Связь между пользователем и provider.

Ключевые поля:
- `providerId`;
- `userId`;
- `role`;
- `status`.

Смысл:
- определяет права пользователя внутри конкретного provider;
- один пользователь не может иметь дубликат membership в одном provider.

### Service

Карточка услуги, публикуемой на платформе.

Ключевые поля:
- `id`;
- `category`;
- `status`;
- `title`;
- `price`;
- `description`;
- `providerId`;
- `createdByUserId`;
- `updatedByUserId`.

Смысл:
- каждая услуга всегда принадлежит конкретному provider;
- услуга не существует вне provider-контекста;
- услуга является публичной продажной единицей provider;
- публикация услуги управляется через жизненный цикл статусов;
- поля аудита должны сохранять, кто создал и кто последним менял запись.

Жизненный цикл услуги:
- `DRAFT` - черновик, не виден в публичной витрине;
- `PUBLISHED` - опубликованная услуга, доступна клиентам;
- `ARCHIVED` - архивная услуга, не участвует в публичной выдаче, но сохраняется в истории.

### ServiceLead

Заявка клиента на услугу.

Ключевые поля:
- `id`;
- `serviceId`;
- `providerId`;
- `customerUserId`;
- `customerName`;
- `customerEmail`;
- `customerPhone`;
- `message`;
- `status`;
- `createdAt`;
- `updatedAt`.

Смысл:
- заявка является первым откликом клиента на услугу;
- заявка создается из публичной карточки услуги или ее CTA;
- заявка всегда связана с конкретной услугой и provider;
- заявка может быть переведена в заказ позже.

Жизненный цикл заявки:
- `NEW` - новая входящая заявка;
- `IN_PROGRESS` - заявка взята в работу;
- `CONVERTED_TO_ORDER` - заявка переведена в заказ;
- `CLOSED` - заявка закрыта без конверсии в заказ.

### Order

Заказ, созданный из принятой заявки.

Ключевые поля:
- `id`;
- `serviceLeadId`;
- `serviceId`;
- `providerId`;
- `customerUserId`;
- `status`;
- `createdAt`;
- `updatedAt`.

Смысл:
- заказ является отдельной provider-scoped сущностью и создается после подтвержденной договоренности по заявке;
- заказ всегда связан с конкретной заявкой, услугой, provider и заказчиком;
- одна заявка может породить не более одного заказа;
- заказ существует как отдельная запись и не должен подменяться одним лишь статусом заявки.

Жизненный цикл заказа:
- `ACTIVE` - заказ создан и находится в работе;
- `COMPLETED` - заказ завершен;
- `CANCELLED` - заказ отменен.

## Главные бизнес-правила

### Общие правила

- Гость может просматривать публичные услуги.
- Зарегистрированный пользователь может пользоваться платформой как заказчик без создания provider.
- Создание provider - это отдельный onboarding-шаг после регистрации.
- Пользователь может переключать активный provider, если у него больше одного membership.
- Все provider-зависимые данные должны быть привязаны к `providerId`.

### Правила для provider

- При создании provider автоматически создается membership автора с ролью `OWNER` и статусом `ACTIVE`.
- При создании provider пользователю автоматически выставляется `activeProviderId` на новый provider.
- `SELF_EMPLOYED` provider не может иметь менеджеров.
- Один пользователь не может владеть более чем одним `SELF_EMPLOYED` provider.
- Добавлять менеджеров может только `OWNER`.
- Membership со статусом не `ACTIVE` не дает доступа к provider-данным.

### Правила для услуг

- Любая услуга обязана иметь `providerId`.
- `providerId` для create/update/delete не должен считаться достоверным, если пришел с клиента.
- Provider-контекст для защищенных операций определяется из пользователя и его активного membership.
- Нельзя обновлять или удалять provider-данные только по `id` без проверки области доступа.
- Публичный каталог услуг доступен всем.
- В публичной витрине показываются только услуги со статусом `PUBLISHED`.
- Услуги со статусами `DRAFT` и `ARCHIVED` не должны отображаться клиентам.
- Управление услугами доступно только пользователям с подходящей ролью в provider или платформенным администраторам.
- Услуга сначала может быть создана как черновик, затем опубликована или отправлена в архив.
- Архивирование предпочтительнее физического удаления, если нужно сохранить историю работы provider.

### Правила для заявок и заказов

- Первый отклик клиента на услугу - это заявка, а не обязательный немедленный заказ.
- Заявка создается по опубликованной услуге.
- Гость может инициировать создание заявки из публичной услуги, но перед фактической отправкой заявки должен пройти регистрацию или вход.
- После успешной аутентификации в сценарии заявки система должна продолжить отложенный flow и создать заявку уже от имени авторизованного пользователя.
- Если заявка создана после auth-gated сценария из публичной услуги, пользователь должен попасть в личный кабинет на раздел своих заявок.
- Заказ является следующим этапом после заявки, а не обязательной стартовой сущностью.
- Поток продаж продукта фиксируется как `услуга -> заявка -> заказ`.
- До конверсии в заказ заявка остается отдельной рабочей сущностью provider.
- При конверсии заявки в заказ система должна создать отдельную запись `Order`.
- После успешного создания заказа исходная заявка получает статус `CONVERTED_TO_ORDER`.
- Конверсия в заказ допустима только для заявки, привязанной к авторизованному заказчику через `customerUserId`.
- Повторная конверсия одной и той же заявки не должна создавать второй заказ.
- Списки заказов должны быть доступны и заказчику, и provider в своих интерфейсных контекстах.

## Пользовательские сценарии

### Гость

Гость может:
- открыть главную страницу;
- просматривать список услуг;
- открыть страницу отдельной услуги;
- перейти к регистрации или входу.

Гость не может:
- управлять услугами;
- работать с provider;
- открывать защищенные профессиональные сценарии.

### Регистрация и вход

Сценарий регистрации:
1. Пользователь вводит имя, email и пароль.
2. Создается аккаунт.
3. Пользователь автоматически логинится.
4. По умолчанию после регистрации пользователь направляется на создание provider.
5. Исключение: если регистрация была начата из auth-gated сценария создания заявки по услуге, система должна вернуть пользователя в customer-flow и завершить создание заявки вместо перехода на provider onboarding.

Сценарий входа:
1. Пользователь вводит email и пароль.
2. Если данные корректны, создается сессия.
3. По умолчанию после входа пользователь попадает на главную страницу.
4. Исключение: если вход был начат из auth-gated сценария создания заявки по услуге, система должна вернуть пользователя в customer-flow и завершить создание заявки.

### Onboarding профессионала

После регистрации пользователь попадает на экран создания профессионального профиля.

На этом шаге он может:
- создать provider;
- пропустить шаг и остаться обычным заказчиком.

Если пользователь создает provider:
1. Заполняет `name`, `slug`, `type`.
2. Система создает `Provider`.
3. Система создает `ProviderMember(role=OWNER, status=ACTIVE)`.
4. Система выставляет `activeProviderId`.
5. Пользователь попадает в профиль.

Если пользователь пропускает шаг:
- аккаунт остается обычным пользовательским аккаунтом без provider-membership;
- позже можно вернуться к созданию provider из профиля.

### Профиль пользователя

Профиль пользователя - это личный кабинет, в котором пользователь действует как частное лицо / заказчик.

В личном кабинете находятся:
- личные данные аккаунта;
- пользовательские заявки как заказчика;
- статус аккаунта;
- пользовательские заказы как заказчика;
- вход в профессиональный кабинет, если у пользователя есть хотя бы один `ACTIVE` membership.

Текущее состояние:
- личный профиль реализован как обзор аккаунта;
- customer-заявки должны отображаться отдельным разделом внутри личного кабинета;
- часть provider-функций пока еще находится внутри страницы профиля как переходное решение;
- customer-заказы отображаются отдельным разделом внутри личного кабинета как MVP-история заказов;
- подробный workflow заказа пока остается минимальным и не считается завершенной бизнес-функцией.

### Разделение личного и профессионального кабинета

В системе используется один аккаунт пользователя, но два разных интерфейсных контекста:
- личный кабинет пользователя;
- профессиональный кабинет поставщика услуг.

Главный принцип:
- система не делит пользователей на два разных аккаунта;
- пользователь всегда имеет один аккаунт, одну сессию и один набор учетных данных;
- разделяется не аккаунт, а рабочий контекст.

Контексты работы:
- в личном кабинете пользователь действует от своего имени;
- в профессиональном кабинете пользователь действует от имени активного `Provider`.

### Профессиональный кабинет

Профессиональный кабинет - это отдельный workspace внутри продукта, в котором пользователь работает как provider.

Профессиональный кабинет строится вокруг `activeProviderId`.

В профессиональном кабинете находятся:
- обзор активного provider;
- управление услугами provider;
- управление командой provider;
- профессиональные заявки / заказы;
- настройки provider;
- переключение между provider, если у пользователя несколько membership.

Правила навигации:
- если у пользователя нет provider-membership, профессиональный кабинет ему недоступен как рабочее пространство;
- если у пользователя есть хотя бы один `ACTIVE` membership, в интерфейсе показывается вход в профессиональный кабинет;
- если у пользователя один provider, кабинет открывается сразу в его контексте;
- если у пользователя несколько provider, кабинет открывается в контексте `activeProviderId`, а переключение provider происходит внутри профессионального кабинета.

Что не должно развиваться внутри обычного профиля:
- управление услугами provider;
- управление участниками команды provider;
- профессиональные заявки и бизнес-процессы provider;
- аналитика и рабочие инструменты provider.

Эти сценарии должны развиваться внутри отдельного профессионального кабинета.

### Работа профессионала

Если у пользователя есть хотя бы один `ACTIVE` membership:
- он считается профессионалом;
- у него есть активный профессиональный профиль;
- он может работать в контексте текущего `activeProviderId`.

Профессионал может:
- просматривать активный provider;
- переключать активный provider;
- просматривать участников активного provider;
- если он `OWNER`, добавлять менеджеров;
- если его роль допускает управление услугами, работать с услугами provider.

### Управление командой

Для `COMPANY` provider:
- `OWNER` может добавить менеджера по email существующего пользователя;
- если membership уже есть, запись может быть обновлена до `MANAGER` + `ACTIVE`, если это допустимо;
- владелец не может добавить самого себя как менеджера;
- владелец не может быть понижен этим сценарием до менеджера.

Для `SELF_EMPLOYED` provider:
- команда не поддерживается;
- добавление менеджеров запрещено.

### Управление услугами

Есть два режима работы с услугами.

Публичные сценарии:
- список услуг;
- просмотр карточки услуги.

Защищенные сценарии:
- чтение списка своих услуг;
- создание услуги;
- редактирование услуги;
- архивирование услуги;
- публикация услуги;
- перевод услуги обратно в черновик;
- удаление услуги как исключение, а не базовый рабочий сценарий.

Текущее правило ролей:
- `PLATFORM_ADMIN` может управлять всеми услугами;
- `OWNER` может читать, создавать, редактировать, публиковать, архивировать и удалять услуги своего активного provider;
- `MANAGER` может читать, создавать и редактировать услуги своего активного provider;
- `MANAGER` может переводить услугу в черновик и публиковать ее;
- `MANAGER` не должен удалять или архивировать услуги, пока это явно не изменено в бизнес-спецификации.

### Работа с заявками

В профессиональном кабинете заявки являются следующим рабочим уровнем после опубликованных услуг.

Provider должен иметь возможность:
- видеть новые заявки по своим услугам;
- брать заявку в работу;
- закрывать заявку;
- переводить заявку в заказ, если сценарий дошел до сделки.

При переводе заявки в заказ:
- provider создает отдельный заказ в своем контексте;
- заявка остается в истории как источник заказа;
- заказ появляется в списке заказов provider и в личном кабинете заказчика.

### Работа с заказами

В MVP заказ является минимальной операционной сущностью после конверсии заявки.

Provider должен иметь возможность:
- видеть заказы своего активного provider;
- различать активные, завершенные и отмененные заказы.

Заказчик должен иметь возможность:
- видеть свои заказы в личном кабинете;
- различать активные, завершенные и отмененные заказы.

## Правила доступа

### Базовые принципы

- UI не является источником истины по правам.
- Скрытие кнопки не считается защитой.
- Все реальные проверки должны выполняться на сервере.
- Доступ к provider-данным всегда должен учитывать provider scope.

### Active provider context

Для профессиональных операций используется активный provider-контекст.

Правило:
- если у пользователя есть `activeProviderId` и он валиден среди `ACTIVE` memberships, используется он;
- иначе используется первый доступный `ACTIVE` membership;
- если memberships нет, пользователь считается не имеющим provider-контекста.

### Scope-защита

Для любой provider-сущности:
- список должен фильтроваться по `providerId`;
- update/delete не должны выполняться по одному `id` без проверки принадлежности к `providerId`;
- при create `providerId` должен устанавливаться из серверного контекста пользователя.

## Что уже реализовано

На текущий момент реализовано:
- регистрация и вход;
- хранение системной роли пользователя;
- provider onboarding;
- создание provider;
- переключение активного provider;
- просмотр участников provider;
- добавление manager в `COMPANY` provider владельцем;
- публичный просмотр услуг;
- серверно защищенное управление услугами с учетом provider scope;
- хранение memberships и active provider в auth context / session;
- создание заказа из заявки как MVP-конверсия `lead -> order`;
- списки заказов для заказчика и provider.

## Что пока не является завершенной бизнес-логикой

Следующие области пока нельзя считать полноценной продуктовой логикой:
- заказы: реализован только MVP-уровень без расширенного lifecycle и операционных сценариев;
- платежи отсутствуют;
- отзывы как самостоятельный пользовательский процесс отсутствуют;
- публичные страницы provider как отдельный продуктовый сценарий не оформлены;
- управление услугами через `/admin/services` сейчас ближе к internal/dev CRUD, чем к финальному пользовательскому кабинету;
- детальная карточка заказа и расширенные действия с заказом пока не доведены до пользовательского UI.

## Roadmap / Planned features

Этот раздел описывает желаемые направления развития продукта.

Важно:
- это не считается уже реализованной бизнес-логикой;
- Cursor не должен автоматически считать эти сценарии существующими в коде;
- до реализации каждая фича должна быть уточнена отдельной мини-спецификацией или обновлением этого документа.

Потенциальные направления развития:

Для заказчика и клиентского опыта:
- расширенный жизненный цикл заказов и дополнительные бизнес-статусы;
- детальная история заказов для заказчика и профессионала;
- отзывы и рейтинг после завершения заказа;
- создание клуба по интересам.

Для профессионального кабинета и provider-инструментов:
- публичная страница provider с его услугами и описанием;
- выделение отдельного маршрута профессионального кабинета (`/pro` или аналогичного) вместо развития provider-функций внутри общего профиля;
- полноценный профессиональный кабинет вместо текущего internal/dev CRUD для услуг;
- расширенное управление командой provider;
- лента заявок между провайдерами.

Для коммуникации и взаимодействия:
- статусы взаимодействия между заказчиком и профессионалом;
- чат между заказчиком и профессионалом;
- уведомления о ключевых действиях в системе.

Для AI и поддержки платформы:
- поиск услуги через чат с искусственным интеллектом;
- обратная связь: предложения по улучшению сайта, помощь, поддержка.

Правило при реализации roadmap:
1. Сначала описать целевой сценарий и ограничения в этом документе.
2. Затем определить роли, доступы и состояние данных.
3. Только после этого менять схему, API и UI.

## Ограничения домена

Не нужно предполагать в системе наличие следующих сущностей, если они не добавлены отдельной спецификацией:
- корзина;
- онлайн-оплата;
- чат;
- заявка со сложным жизненным циклом;
- календарь бронирования;
- многоступенчатое согласование заказа;
- публичный рейтинг provider;
- сложная организационная иерархия компании.

Если такие функции понадобятся, они должны быть сначала описаны в этом документе, а потом реализованы в коде.

## Правила для Cursor

### Что считать источником истины

При изменении доменной логики Cursor должен опираться в первую очередь на:
1. `docs/business-logic.md`
2. `frontend/docs/roles-and-permissions.md`
3. текущую схему и реализацию, если они не противоречат этим документам

### Что Cursor должен делать

- Опирайся на текущую доменную модель: `User`, `Provider`, `ProviderMember`, `Service`.
- Разделяй системные роли платформы и роли внутри provider.
- Любую provider-зависимую сущность связывай с `providerId`.
- Все серверные проверки доступа строй через provider context.
- Не доверяй `providerId`, пришедшему с клиента, в protected create/update/delete.
- Разделяй "уже реализовано" и "целевая логика", не выдавай заглушки за готовые продуктовые функции.
- Если меняется бизнес-логика, сначала обнови этот документ, потом код.

### Что Cursor не должен делать

- Не придумывай новые роли без обновления этого документа.
- Не добавляй новые статусы заказа, оплаты, сделки или бронирования без отдельной спецификации.
- Не считай `/admin/services` финальным пользовательским кабинетом по умолчанию.
- Не делай авторизацию только на уровне UI.
- Не разрешай update/delete provider-данных по одному `id` без scope-проверки.
- Не разрешай менеджеру удалять услуги, пока это явно не изменено в спецификации.
- Не добавляй менеджеров в `SELF_EMPLOYED` provider.
